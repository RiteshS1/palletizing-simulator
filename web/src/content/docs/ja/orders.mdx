# 注文とウェーブ

パレット1枚は積み付けの問題ですが、1シフト全体は **スケジューリング** の問題です。次にどの注文を処理し、どのパレットに載せるか。それを決めるのが **倉庫実行システム（WES）** です。

## 業務ルール

- 1枚のパレットは **1つの届け先**（トラックの1つの停車先）の注文だけを載せる。
- 1件の注文を複数のパレットに **分割しない**。顧客は注文をまとめて受け取る。
- ロボットは1台で、1箱ずつ約6秒かけて配置する。

## 方針1：1件ずつ（オンライン）

注文は **優先度付きキュー** で待ちます。最も緊急のもの（優先度1が3より先、次に期限が早いもの、最後に先着順）から取り出します。取り出した注文は、届け先の空いているパレットに載せます。**ベストフィット**（載せたあと最も満杯になるパレット）か、**ファーストフィット**（最初に収まるパレット）です。

```cpp
// std::priority_queue は最大ヒープ：比較関数は「a は b より緊急度が低いか？」に答える
struct LessUrgent {
    bool operator()(int a, int b) const { return moreUrgent(orders[b], orders[a]); }
};
```

## オンライン積み付けの落とし穴

1件ずつの方式は **うまく積めません**。24件の注文で、パレット15枚、平均積載率19%です。最初の注文は上面を凸凹にし、次の注文の箱は支持と耐荷重のルールを満たせません。注文は分割できないので、1つの箱が失敗すると注文全体が失敗します。これは **オンライン** の積み付け（次に何が来るか分からない）で、オフラインの積み付けよりはるかに難しい問題です。

## 方針2：ウェーブ（バッチ処理）

届け先ごとに、およそ1パレット分がたまるまで、または期限が迫って開始せざるを得なくなるまで注文を保留し、まとめてオフラインのエクストリームポイント法で計画します。収まりきらなければ、最も緊急度の低い注文を外して計画し直します。

| 24件の注文、シード7 | 1件ずつ | ウェーブ |
|---|---|---|
| パレット | 15 | **7** |
| 平均積載率 | 19% | **42%** |
| シフト時間 | **17分** | 25分 |
| 遅延した注文 | 0 | 0 |

これは典型的な **レイテンシと効率のトレードオフ** で、データベースのグループコミットや TCP のネーグルアルゴリズムの背後にあるのと同じ考え方です。

## イベント駆動シミュレーション

時計を1秒ずつ進める代わりに、シミュレーションは次に意味のある時刻へ直接ジャンプします。次の注文の到着、または待っている注文が期限に間に合うために開始しなければならない瞬間です。

## 使っているデータ構造

- **二分ヒープ**（`std::priority_queue`）：追加と取り出しが O(log n)。
- **ハッシュマップ**（`std::unordered_map`）：届け先 → 開いているパレットや待機中の注文。参照は平均 O(1)。
